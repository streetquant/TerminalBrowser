# T1000 0.2.20

Release date: 31 August 2026

## Decision

0.2.20 is the Warp Drives managed-release compatibility candidate. Promote it
only with the managed launcher and storage attestation in place, the primary
database migration gates passing, and the recovery-intent and concurrency
checks passing. Pre-existing legacy auth scopes are rebound only for an exact
native Codex resume after the recovery coordinator proves durable ownership
and a missing, dead, quiescent backend. Other session types remain fail closed.

## User-visible changes

- Managed releases use an absolute `T1000_MANAGED_ROOT` and fail closed when
  the launcher/bootstrap or root is not the expected non-rotational SSD cell.
- Session recipes preserve an absolute logical `cwd`. Launch and recovery
  require that exact directory, with no parent, home-directory, or `/` fallback.
- Recovery work is bounded and deduplicated. Different targets can recover in
  parallel, while durable per-target claims keep the same session, tmux pane,
  auth scope, or resume target single-flight.
- Automatic startup recovery honors an explicit durable active recovery intent
  matching the stored session fingerprint, name, and logical cwd. Stopped and
  start-error rows require that active intent; inactive or malformed intents
  block recovery, while legacy active-status rows retain their narrow
  compatibility path. New, remembered, external, and archived records do not
  become runnable through incidental startup discovery.

## Warp Drives release root

The managed launcher requires an absolute `T1000_MANAGED_ROOT`; the default is
`/home/arch/.local/state/codex-project-homes/runtime/t1000-managed`. It verifies
that the launcher, bootstrap, and root are real, current-user-owned paths on
the same expected non-rotational backing device and fails closed otherwise.
The mutable TermDeck state directory is the managed root's adjacent
`<T1000_MANAGED_ROOT parent>/termdeck/` directory:

- `sessions.sqlite3` is the managed primary session registry.
- `terminal-auth/` contains newly provisioned private auth scopes.
- `recovery-intents/` contains durable explicit recovery requests.

TermDeck records the runtime attestation tuple
`CODEX_STORAGE_FABRIC=warp-drives-v1`,
`CODEX_WORKSPACE_STORAGE_CLASS=ssd-cell`, and
`CODEX_BULK_STORAGE_MASKED=1` as advisory evidence. TermDeck admission is
controlled by path, ownership, mount, device, and rotational proof so a legacy
control-root parent cannot falsely reject healthy SSD state. Every managed
Codex workspace process launched from a pane must still receive the exact tuple
from the canonical Codex launcher.

## Exact logical cwd

Recipes persist the user's absolute logical working-directory spelling rather
than silently replacing it with a resolved parent. Before launch or recovery,
TermDeck checks that exact directory. Missing, inaccessible, or otherwise
invalid directories fail closed; there is no fallback to a parent directory,
`$HOME`, or `/`. The same exact logical cwd is included in recovery-intent
matching, so an intent cannot authorize a different checkout or workspace.

## Primary-only database migration

Legacy import is deliberately narrower than a state-tree migration:

- Only the genuinely new TermDeck primary GUI performs the explicit copy from
  the legacy `sessions.sqlite3` registry to the managed primary database.
- The source is checked for a valid SQLite database, copied through an atomic
  temporary destination, rechecked for integrity and unchanged source state,
  and published with retry-safe locking and fsync boundaries.
- An existing managed destination is validated and left untouched; the legacy
  source remains available for rollback and audit.
- The migration never copies or moves `terminal-auth`, Codex configuration,
  conversation roots, or other legacy state. Secondary activations do not
  repeat the migration, and CLI construction does not become an independent
  migration authority.

## Bounded recovery and intent

Recovery uses a bounded process-local worker pool (default four workers, with a
configured cap of sixteen) together with durable per-target claims and expiry.
Different workspaces may recover concurrently. Requests for the same session,
tmux target, auth scope, or resume target coalesce into one in-flight recovery,
and claims are released or renewed around the operation so a stale owner does
not permanently block retry.

Recovery intent is an explicit durable sidecar tied to the managed primary
database. An intent records and verifies the exact session identity,
fingerprint, name, and logical cwd before it can become active. Only the
managed primary consumes an accepted intent and marks it active; stop and
normal lifecycle transitions clear or preserve the inactive/legacy state as
appropriate. Active intent is required to revive stopped or start-error rows;
older active-status rows retain only their narrow compatibility path.
Incidental status, archive, or broad filesystem discovery cannot create a new
active recovery intent.

## Authentication boundary

The 0.2.19 authentication contract remains: each terminal keeps a private
selection boundary while canonical Codex configuration and account material
are shared through verified bindings, and same-pane account switching preserves
the exact session identity or rolls back. Newly provisioned scopes may use the
managed `terminal-auth/` tree.

Existing auth scopes and their recorded `codex_home` paths are not moved by the
database migration. For an exact native Codex resume, the recovery coordinator
may create a sparse private scope under managed SSD state only after it holds a
durable per-target claim and independently proves that the prior backend is
missing, dead, and quiescent. The new scope preserves the selected account,
shares canonical session and account roots, hydrates only the required private
SQLite state, and publishes the registry update with compare-and-swap plus a
durable receipt. The old scope remains untouched as rollback evidence.

External sessions, `codex-opencode`, unknown account selections, inexact resume
commands, incomplete lifecycle proof, or a lost claim defer without changing
the registry. A claim lost after sparse staging may leave an unreferenced SSD
scope for authenticated maintenance, but it never becomes the session's
active binding. No whole auth tree is copied, moved, or deleted.

## Preserved contracts

- Existing session, tmux, account, and conversation identities remain stable.
- Recovery never substitutes a different cwd or silently starts a new session
  for an unmatched intent.
- Legacy state remains available when managed import is unavailable or fails.
- The database migration is the only legacy import path and has no auth-tree
  side effects.

## Validation gates

- When the host namespace does not expose a conventional mode-`1777` `/tmp`,
  set `T1000_VALIDATION_RUNTIME_BASE` to a short, existing, current-user-owned
  mode-`0700` directory on Warp Drives storage. The runner validates the path
  before creating or reclaiming any task runtime.
- Parse and compare the `0.2.20` project and package versions.
- Verify the changelog and this release note cover the managed root, exact cwd,
  primary-only migration, bounded recovery, explicit intent, and guarded SSD
  auth-scope rebind boundary.
- Run the candidate's focused migration, recovery-coordinator,
  recovery-intent, auth-rebind, session-recipe, and managed-launcher tests
  before promotion.
