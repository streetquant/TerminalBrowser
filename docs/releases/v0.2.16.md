# T1000 0.2.16 — independent tmux and GUI lifecycles

## Release decision

This release is accepted only when a clean source commit passes the complete canonical production contract, two controlled builds are byte-identical, the immutable managed install verifies, the old GUI exits through the application action, and every live tmux session and pane identity remains stable across activation.

## Ownership model

```text
T1000 GUI service  ── presents/attaches ──> tmux sessions
       │
       └── may stop or upgrade independently

user-systemd delegated tmux scope/anchor
       └── tmux server ── owns ──> persistent pane payloads
```

The GUI no longer owns the tmux server by cgroup ancestry. A first server is born in a delegated transient scope when socket mounts are shared; otherwise it is moved immediately into a delegated process-only anchor. A legacy server follows the same exact PID and start-time migration path without restart. Commit requires the same PID, the same start time, the expected cgroup, and a verified active unit.

## Activation model

The application exports `quit-preserving-sessions` through `org.gtk.Actions`. Activation persists live metadata, destroys the GTK windows, and releases GUI resources while leaving tmux sessions intact. A verified replacement GUI then attaches to the existing authority.

## Recovery model

Managed rows are addressed by stable tmux session names, never durable server-local pane IDs. Plain shell recreation is restricted to trusted configured system shells with no recovery tuple. Agent recovery remains exact and fail-closed: UUID-bound Codex or Claude state may resume, while incomplete historical launch metadata is retained for inspection rather than replayed as a different conversation.

## Verification requirements

- unit tests for first-server wrapping, direct fallback, safe no-op, legacy migration, PID reuse, and GUI action routing;
- real disposable user-systemd/tmux lifecycle smoke covering private socket mounts, delegated scope-or-anchor placement, and bounded cleanup;
- canonical CI and production validation with an unchanged source fingerprint;
- byte-identical release builds and strict wheel/manifest verification;
- live activation proving stable tmux server/session/pane identities, zero dead panes, zero visible recovery-pending records, one verified GUI, and a preserved rollback generation.
